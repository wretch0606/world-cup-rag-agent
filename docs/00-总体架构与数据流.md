# 世界杯知识库 — 总体架构与数据流

## 职责链

```
A 前端 (Vue/D3.js)
  ↕ final_response.json         ← B 组装统一响应（含 graph, intent, trace_id）
B FastAPI / LangGraph (路由、SQL查询、实体识别)
  ↕ rag_result.json             ← E 仅负责答案、facts、sources、evidence、告警
E RAG 生成与评测 (事实融合、最终答案、来源、告警)
  ↕ retrieval_result.json       ← D 返回候选列表 + 评分，不生成 answer
D Chroma 检索 (Query Rewrite → 向量召回 → Reranker)
  ↕ match_facts.jsonl           ← C 提供标准化事实文本
C 数据工程 (SQLite、清洗、标准化事实)
```

## 三层契约

| 契约 | 方向 | 文件 | 核心内容 |
|------|------|------|----------|
| 入库契约 | C → D | `match_facts.jsonl` | 标准化事实文本 + metadata（含 source_id, source_url） |
| 检索契约 | D → E | `retrieval_result.json` | 候选 EvidenceItem 列表 + 分数 + 实际执行状态 |
| 生成契约 | E → B | `rag_result.json` | 答案 + 事实 + 来源 + evidence + 告警 + 耗时 |

## 关键原则

1. **精确事实走 SQLite**：比分、日期、阶段、胜者等由 B 的 SQL Service 直接返回，不经过 RAG
2. **source_id 必须全链路保留**：C→D→E→B，最终出现在前端来源展示中
3. **D 不生成答案**：D 只负责检索和排序，答案由 E 生成
4. **E 不负责 graph/intent/trace_id**：这些由 B 组装
5. **枚举在 DB 和 API 中用英文**：中文显示名通过 `*_name` 字段提供
